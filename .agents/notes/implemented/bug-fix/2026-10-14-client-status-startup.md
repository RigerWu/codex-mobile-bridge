# Agent Note: 客户端状态读取避开启动锁

Status: implemented

## Problem

Windows 安装包验收中，已认证的 `GET /api/clients` 超过测试端 12 秒读取期限；网关在响应时遇到客户端断开。该请求与客户端启动、账号检查和原生进程检查共用 `client_lock`，冷启动时会排在长操作后面。单次 Windows 进程清单读取约为一秒以内，不能据此认定它是整个超时的唯一原因。

## Decision

`GET /api/clients` 只尝试无等待地读取当前缓存。缓存失效或锁正由启动、账号或生命周期操作持有时，它立即返回最后一次完整展示快照；首次没有快照时返回空列表，并以 `pending: true` 明确表示结果尚在后台生成。后台刷新单飞运行，调用原有 `clients(refresh=True)`，完成后的请求返回完整状态和 `pending: false`。后台失败提供 `refreshError`，并间隔两秒再允许下一次刷新。关闭后的管理器不启动刷新，也不发布后台晚到快照。

Web 在 `pending: true` 时保留当前列表、选择和操作结果未知标记，复用已有两秒快速轮询；仅完整结果参与状态应用和操作结果核对。展示快照从不用于启停、退出、账号切换或其他写操作的安全判断；这些路径继续使用原有锁、实时检查和原子规则。

## Existing-note audit

已用隐藏文件检索活跃笔记。`quiet-client-list-status` 和 `shared-client-list-refresh` 涉及聊天列表，不决定本次应用状态 GET 的锁与刷新语义；无需修改。

## Alternatives considered

延长 Web 或验收脚本的读取超时能容纳某次较慢的启动，却仍让只读请求排队等待长锁，冷启动界面无法及时得知状态。直接把现有 15 秒展示缓存用于所有路径可使读取更快，但若写操作据此决定进程和账号状态，会破坏即时核验要求。

## Consequences

GET 在刷新期间可能展示稍早的完整快照；`pending` 表示该快照不可作为新状态确认。首次读取可暂时没有客户端行，Web 不应把它当作用户关闭了应用。定向回归覆盖锁长期占用、单飞刷新、完整状态恢复、后台异常后的受控重试、关闭边界、写操作仍实时检查和 Web 对选择及未知结果的保留。真实 Windows 网关延迟需在新的测试包中复验。
