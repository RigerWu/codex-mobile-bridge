# Agent Note: Optional local CLI account synchronization

Status: implemented

## Problem

Codex Desktop and the local Codex CLI share one configuration home. A Desktop switch changes the CLI files even when the user does not select CLI synchronization, while an already running CLI daemon may keep older settings. Claude Desktop official cookies are not Claude Code CLI credentials; API profiles can be copied only after verifying the saved Desktop profile.

## Decision

Desktop switch requests can explicitly select local CLI synchronization. Codex reports the shared configuration and, when selected, verifies the CLI account/provider/config separately after Desktop verification. A CLI failure leaves the verified Desktop switch in place and is reported as a partial failure. When CLI synchronization is not selected, the UI says the shared configuration changed but the CLI runtime is unverified.

A CLI-only Codex switch with Desktop stopped uses the existing account preparation and native credential snapshots, applies them to the shared home, verifies them through a fresh native account/config RPC, and restores the snapshot on failure. A running Desktop uses its established stop/apply/restart transaction. Joined CLI sessions, pending tasks and a live CLI control daemon block switching. The helper never terminates an external daemon or touches SSH configurations.

Claude Desktop synchronization accepts only the currently effective, fingerprint-matched saved API profile. It creates a managed Claude Code profile and selects it after Desktop succeeds. Native OAuth/cookie profiles remain separate and are selected read-only. Claude Code API settings use its documented base URL, authentication and model environment variables. No model request is used for verification.

The local CLI access controls are shown inside each provider's account management view in the web, mobile and gateway desktop interfaces. Codex and Claude Code have separate fixed-provider panels. A saved API access can explicitly query its upstream model-list endpoint or test that endpoint using its private saved credential without selecting the access or sending a conversation request. This test confirms model-list endpoint connectivity and authorization only; users can still enter a model ID manually when the endpoint is unavailable.

## Verification

Targeted Python fixtures cover Codex rollback, live-daemon blocking, managed Claude API settings, Desktop API import, and separate Desktop/CLI outcomes. UI fixtures cover opt-in checkbox submission. An isolated native Codex acceptance fixture with a loopback model server confirmed that a fresh CLI turn uses its selected model and endpoint, with external connection attempts blocked. That fixture did not exercise an account switch. Real account changes, paid model calls, existing daemon reload, and SSH configuration changes were not run.

## Cross-platform account guard follow-up

The CLI-only switch asks the Codex CLI session layer whether its native daemon may still be running. It blocks on uncertain status and no longer assumes a Unix socket in the account layer. Native verification checks both the selected API provider URL and the `openai_base_url` route used by existing Codex chats, plus the account type. Claude Code API verification uses the same managed-provider environment as its launch path and checks the configuration directory returned by `auth status --json` before selecting the profile. Imported Claude directories reject a symlink at the supplied path before resolution.

The cross-platform account fixtures cover daemon-status blocking, both effective Codex API routes, Claude's reported configuration directory, and symlinked import rejection. On macOS, the installed Claude Code 2.1.287 returned `authMethod=api_key` and `authMethod=oauth_token` respectively for isolated temporary profiles with placeholder keys; no model request or actual account change was made. The supported environment keys and provider-routing overrides were checked against the [official Claude Code environment variable reference](https://code.claude.com/docs/en/env-vars). Those macOS checks alone did not establish Windows or Linux behavior; the Linux Codex acceptance result follows below.

On a Linux server x86_64 with Python 3.10.12 and installed Codex CLI 0.160.0, `tests/acceptance/cli_sync_native.py` passed from `<test-root>/accounts` using an isolated `CODEX_HOME`, two separate loopback Responses API servers and placeholder keys. It verified native A routing, an injected B failure restoring A files and a subsequent native A turn, then a successful B switch and native B turn. It also blocked a joined CLI session and unknown daemon state produced by a temporary PID artifact, with the installed CLI's read-only daemon status probe; 25 external CONNECT attempts were denied by the local mock proxy. It did not start a real live daemon, touch the daily account directories, call paid models, or validate Claude Code account switching. Native Linux CLI credential behavior for these fake API profiles and rollback is verified; real account login and live-daemon lifecycle remain untested.

On Windows 10.0.19045 x64, the installed Codex MSIX package contains `app/resources/codex.exe` version 0.162.0-alpha.17.2. The SSH session could read but not execute it from `WindowsApps`; a byte-for-byte copy to `<test-root>/accounts/codex.exe` ran without installation. With Python 3.11 and the same isolated fixture under that temp directory, native A and B turns reached their respective loopback endpoints with matching placeholder credentials and models. The injected B failure restored A and another native A turn; joined-session and unknown-daemon guards blocked switching, and 23 external CONNECT attempts were denied. This demonstrates the copied native binary's app-server path and file-based API account transaction. It does not establish that the copied binary is a supported managed daemon package, nor verify a genuinely running daemon, the desktop restart path, or real credentials.

Claude Code 2.1.168 on Windows omits `configDirectory` from `auth status --json`, unlike 2.1.287 on macOS and Ubuntu. With a selected temporary API profile, 2.1.168 reports `api_key` or `oauth_token` for the respective fake credential; a separate empty temporary profile reports `loggedIn=false` and `authMethod=none`. The account verifier accepts an omitted directory field only when this second native probe proves profile isolation with the same executable and sanitized environment. A present directory field must still match exactly. Regression cases reject an ambient login that persists in the empty profile, malformed or timed-out control output, a wrong selected method, and a present null or mismatched directory.

On Ubuntu x86_64 with Python 3.10.12 and the scoped official Claude Code 2.1.287 binary, `tests/acceptance/claude_sync_native.py` passed entirely under `<test-root>/accounts/`. Native A and B turns reached separate loopback endpoints with the selected x-api-key or bearer token and default model from settings, without a CLI model override. An injected B verification failure restored exact A settings and another native A turn. The native switch-back restored original settings, and a simulated active gateway-owned Claude session blocked preflight. Fourteen external CONNECT attempts were denied.

The same fixture passed on Windows 10.0.19045 with Python 3.11 and installed Claude Code 2.1.168 under `<test-root>/accounts/claude`, after integrating the native Windows writer guard from commit `3c99462` into the isolated source. Native A and B requests used the selected endpoints, fake x-api-key or bearer credentials, and default models; the injected B failure restored A and another native A turn. A completed native turn's session registry did not block the subsequent switch, while a simulated active gateway-owned session did. Thirteen external CONNECT attempts were denied. Neither Linux nor Windows run changed daily profiles or called a paid model. A genuinely active external writer and real credentials were not exercised by this account fixture; the platform guard has separate native identity tests.

Account configuration JSON and native Claude authentication output are read explicitly as UTF-8, independent of the Windows system code page. The legacy negative-control probe retains the same encoding and requires native exit status 1 together with logged-out JSON.
